# 本机引擎启动与可写目录

共享客户端的模型记录属于特定引擎生命周期。健康 GET 或推理连接无法建立 TCP 连接、
已有连接读写中断或服务端提前关闭响应（`httpx.NetworkError`、`httpx.ConnectTimeout`
或 `httpx.RemoteProtocolError`）时清除已加载模型、参考音频与工作
音色记录，下一次合成在原有引擎锁内重新准备目标音色；这个只读探测本身不发送模型
加载请求。读取或连接池超时以及 HTTP 503
不能证明引擎已重启，因此保留记录，避免忙碌时反复加载。程序发出 restart/exit 控制
命令，或本机重启完成验证并即将停止/启动相关进程时，同样先清除记录；拒绝的重启及
无关地址上的引擎不受影响。加载记录失效不改变数据库里保存的启用音色。

健康探测固定它开始时的地址与模型状态版本。迟到的连接失败不能抹去后续模型请求
确认；只在本地跳过重复加载不算远端确认，不能否定连接失败。
回退 GET 也不能跨到新配置的地址。生命周期代际阻止旧模型请求在重启后发布成功或
回滚旧引擎。未观察到连接失败且由外部悄然替换模型/重启的服务，仍无法仅凭在线
状态识别，本协议不宣称远端模型认证。

普通合成保留已有的一次网络重试，但重试前必须重新确认/准备模型。流式连接失败
不自动重播已输出的音频，下一次请求同样重新准备，不要求先打开设置页做健康轮询。
已输出部分音频后读连接中断，也只将本次流标为失败，不拼接新请求或重复播放前半句。

G2V 通过引擎自带 Python 启动可信的本机 `api_v2.py`，工作目录始终保持为用户选择的引擎目录。模型、参考音频和依赖的相对路径仍在这个目录解析。

启动器将 `NUMBA_CACHE_DIR`、`TEMP`、`TMP` 和 `TMPDIR` 放到 G2V 的 `data/engine_cache/`，并实际创建临时文件检查可写性。目录存在不等于可写；某些 Windows Python 3.9 运行时在不可写目录创建临时文件时会长时间重试。

部分旧版入口将 `_temp_dir` 强制设为 `os.path.join(now_dir, "TEMP")`，覆盖启动器提供的目录。`prepare_engine_entrypoint` 只识别这一条已知的模块级赋值，在缓存中生成优先读取 `TMPDIR` 的入口副本。未匹配的入口直接运行原文件。引擎安装目录中的脚本不被修改；源内容和原路径参与缓存文件名，更新引擎后会生成对应的新副本。

`tts_infer.yaml` 同样复制到缓存目录，在副本里应用设备和精度，并通过 `-c` 交给引擎。相对模型路径保留，原配置不被启动器改写。缓存内容由本机引擎产生，可能包含本地路径，不能当作发行源码或素材提交。

源码发行包的 `scripts/package_release.py` 通过明确的程序根目录及文件类型选择输入，整个 `data/` 不作为打包输入。`data/engine_cache/` 中的配置和入口副本不会进入源码 ZIP；空运行目录由打包器重新生成占位文件。角色、背景、皮肤、参考音频和工具私有目录也不进入发行包。

运行状态接口以实际服务探测为就绪依据。受管进程存活但超过三分钟仍未响应时，状态为 `loading_slow`，不把它误报为就绪或确定失败。前端同步显示标签和提示，旧的刷新请求不能覆盖新一轮重启进度。日志中每次启动插入分界标记，失败诊断只使用最近一次启动后的内容。

全局设置弹窗可见时立即读取运行状态，当前一轮读取完成后每五秒再读取一次；关闭弹窗后清理计时器并使旧响应失效。浏览器标签页隐藏时跳过读取，恢复可见后在下一轮检查。引擎重启期间由已有的就绪轮询负责进度，避免两组轮询争用显示。普通刷新只使用 GET，不保存配置、重新加载模型或重启进程。

就绪轮询在断连、GET 超时、HTTP 429 或 5xx 时显示前端状态 `checking`（待确认），并在原有三分钟总时限内继续只读核对。每次读取的超时和间隔均受剩余总时限约束，时钟使用单调计时；持续无法读取时报告“无法确认”，不宣称引擎崩溃。无效的状态载荷同样不能当作已就绪或正在加载。HTTP 400/401/403/404 等拒绝、主动取消及接口明确返回的 `failed`/`unavailable` 会立即停止等待。

重启 POST 的响应若断连、超时或返回 5xx，前端不重发写请求，而是核对当前引擎状态。查询到在线只证明当前服务可用，不能证明本次重启或请求的计算方式已生效，因此保留“重启请求结果未确认”的说明，不把请求的计算方式回填为已确认值；实际启动参数仍由硬件状态接口提供。未发送的排队操作及明确的 HTTP 拒绝不进入此恢复流程。

`EngineLaunch` 记录特定进程的绑定地址、计算方式和单调启动时间。`get_managed_engine_launch`
只在本地端点的主机、端口与记录匹配，且记录仍属于当前受管进程时返回；允许返回已退出
的匹配进程用于诊断。精度查询还要求该进程存活。缺失或过时的记录不能证明新地址正在
加载，也不能把旧端口的日志用于解释新地址的故障。

重启互斥锁同时记录操作的目标地址；当前地址切换后，其他地址上的重启不会遮住本次
服务探测。状态接口在网络探测及日志读取后重新核对重启目标与启动记录，旧进程的
迟到结果不能作为新进程的就绪或失败结论。`engine-status` 返回 `base_url` 和 `source`，
前端以该结果所附的地址显示状态，避免并行遥测跨越地址切换时出现状态与地址不一致。
重启到不同端点前，先确认目标端口未被外部程序占用，再更新启动设置、停止原引擎。

计算方式的保存与生效也分别处理：保存设置只写 G2V 的数据库和首选项缓存；启动器在创建进程时准备配置副本，并记录该进程实际收到的设备及精度参数。状态接口的 `hardware.inference_precision` 只在记录属于当前受管进程且服务地址匹配时提供，`precision_source` 为 `managed_launch`；外部、已退出或不匹配的进程返回空值和 `unknown`，不从保存值猜测。`next_inference_precision` 表示按当前设置解析的下次启动模式，`precision_pending_restart` 表示已知启动参数是否与它不同。这里记录的是启动配置，不是引擎内部数值计算的测量结果。自定义数据目录通过显式数据库路径参与启动设置解析。

回归验证位于 `tests/test_engine_runtime.py`、`tests/test_engine_recovery.py`、`tests/test_precision_runtime.py` 和 `tests/test_runtime_recovery.mjs`。引擎临时目录被占用的反例使用真实 Python 子进程执行合成入口：原入口失败、适配副本成功，同时检查原文件不变。`tests/test_precision_dashboard_browser.py` 用生产设置页和控制器检查桌面及窄屏下的待重启、待确认状态。

`tests/test_settings_telemetry.mjs` 检查弹窗轮询生命周期和迟到响应；`tests/test_engine_status_browser.py` 在桌面宽度的独立浏览器中使用生产设置页、真实控制器和合成 API，验证无需手动刷新即可从启动中转为在线，关闭后不再读取、重新打开立即读取。
`tests/test_engine_poll_recovery.mjs` 检查短暂读取故障、总时限、明确拒绝、取消、真实失败及重启响应丢失；浏览器测试另外通过真实按钮触发重启，检查待确认提示、按钮忙碌状态、恢复在线与单次 POST。
`tests/test_engine_endpoint_ownership.py` 使用合成进程和隔离目录，检查地址、进程及日志归属，
探测/诊断与重启交错，旧启动时间失效，新端口占用时保留旧引擎，以及迁移到空闲端口的
正常路径。前端回归还检查状态卡显示与引擎结果一致的地址。
