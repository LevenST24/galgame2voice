# 流式等待与语音任务预算

HTTP 读取和回复进展是不同的等待。每次网络读取仍有原有的 120 秒空闲时限；服务端
五秒一次的 `: keep-alive` 只能保活连接，不能证明模型或语音工作在推进。

支持新协议的 `/api/chat/stream` 返回 `X-G2V-Progress-Policy: 1` 与
`X-G2V-Voice-Job-Timeout-Ms`。客户端收到有效策略后，文字增量、有效台词以及完成的
音频任务续期 120 秒的进展预算。空文字、未知事件、错误 JSON 和半包不续期。
这不是整轮回复的总时限；持续有进展的长回复可以继续。

推理模型只输出思考内容（OpenAI 兼容流的 `delta.reasoning_content` / `delta.reasoning`，
Anthropic 的 `thinking_delta`）时没有文字增量。服务端为此发送 `progress {stage: "thinking"}`，
同一回复每 5 秒最多一条，不含思考正文；客户端把 `stage` 非空的 `progress` 计为进展。
思考正文不进入台词、语音或记录。

同一会话已有一轮在进行时，后一条流式请求要先等会话锁。等待期间每次醒来发送
`progress {stage: "queued"}`，间隔与保活相同（5 秒），不含台词。客户端同样把它计为进展，
因此排队不会在约两分钟后被当成网络故障。排队没有另设总时长上限：持锁的那一轮仍用自己的
超时和取消，排队方等到它结束。

语音合成可合法等待比两分钟更久。后端在每个可配音任务前发送
`voice_job {index, status: "started"}`，完成后发送同索引的 `finished`。任务开始后有
固定的独立等待预算，普通文字进展不能把它缩短，重复开始或完成公告不能再次续期。
任务结束后回到普通进展预算；即使语音预算仍在，真正的网络断流仍按读取时限处理。

任务预算在 `tts_pipeline.py` 统一定义：两个模型切换窗口、一次推理读取窗口，外加
一分钟排队与 IO 余量，目前合计 600 秒。这是覆盖排队和推理的单句总预算。后端自己
也执行该上限，超时先收尾本次拥有的任务，再将该句语音标记为失败，保留文字并继续
后续句子。异步取消不能强制终止已经进入操作系统的磁盘调用，线程仍按既有生命周期收尾。

没有策略头的旧后端无法公告慢语音，客户端给予最多十分钟无进展的兼容窗口，同时
仍保留两分钟网络读取时限。未知策略版本或不被支持的语音预算按旧协议处理，避免
新前端把旧后端仍允许的慢推理错误缩短。前后端预算兼容性由跨文件回归检查。

超时产生 `stream_idle_timeout`，保留已收到文本、台词和音频；中断请求、关闭读取器，
不自动重新发送聊天或语音合成。用户手动停止仍是取消，不伪装为超时错误。

验证使用确定性时钟、合成语音与临时数据。`test_stream_progress.mjs` 覆盖进展与兼容
预算；`test_stream_progress_policy.py` 覆盖 HTTP 策略、语音收尾与预算一致性。
`test_stream_progress_browser.py` 使用真实 HTTP 心跳和原生 fetch，验证超时发生后服务端
已观察到连接断开；同时覆盖超过普通等待时限的正常慢语音与卡住的语音任务。
